# SolidDesign Auth Redirect & Mail Delivery Configuration

**Status:** current runtime contract  
**Date:** 2026-08-29

## Purpose

Supabase Auth email flows must return users to an approved SolidDesign **internal** origin, and Auth e-mail delivery must be reliable enough for the operating environment.

These are two separate concerns:

```text
redirect contract  = where an accepted Auth link returns
mail delivery      = whether the Auth message can be sent reliably
```

Do not diagnose an e-mail quota failure as a redirect failure, and do not solve a redirect problem by introducing a new mail service.

Auth redirects are deployment configuration, not user/prospect identity. A stale/local Supabase Site URL must never determine a production invitation destination.

## Application redirect contract

`team-invite` always passes an explicit `redirectTo` to `supabase.auth.admin.inviteUserByEmail`.

The browser sends its own `window.location.origin` explicitly as `invite_origin`. The Edge Function validates that value against the narrow SolidDesign internal-origin allowlist. When the HTTP `Origin` header is present, it must match the explicit `invite_origin`. This avoids relying on an implicit header as the source of truth while still preventing arbitrary caller-supplied redirects.

Allowed runtime origins are deliberately narrow:

```text
https://soliddesign-cms.pages.dev
https://pr-<number>.soliddesign-cms.pages.dev
https://cms.<brand>.nl        # after brand cutover, configured explicitly
```

`redirectTo` is the validated `URL.origin` **verbatim**. Do not append a synthetic trailing slash or path. Supabase compares the requested redirect with its configured Redirect URLs; using one canonical origin representation prevents an otherwise valid preview origin from falling back to the Site URL because of a representation mismatch.

The Edge Function returns the selected safe `activation_origin` to the Team UI after creating the invite. The UI must show that value. An invite test is not considered valid unless the server-confirmed activation origin is the environment being tested.

This means the environment from which the operator presses **Uitnodigen** intentionally determines the activation return environment. Production invites return to production; PR-preview invites return to that exact PR preview.

PR previews share the same operational Supabase state plane during this rollout, so they can look deceptively similar to production. Every `pr-<number>.soliddesign-cms.pages.dev` Operator UI must therefore display an explicit `TEST · PR-<number>` marker and prefix the browser title. Production must not display that marker.

The future custom CMS hostname is supplied to the Edge Function through:

```text
SOLIDDESIGN_INTERNAL_ORIGIN=https://cms.<brand>.nl
```

Do not infer internal redirect destinations from prospect/public domains.

## Required Supabase Auth URL configuration

Hosted project: **Authentication → URL Configuration**.

Current rollout:

```text
Site URL
https://soliddesign-cms.pages.dev/

Redirect URLs
https://soliddesign-cms.pages.dev
https://pr-28.soliddesign-cms.pages.dev
https://pr-*.soliddesign-cms.pages.dev
```

The exact `pr-28` entry exists for the current acceptance test. The preview wildcard permits future numbered PR origins without expanding access to unrelated hosts. Because SolidDesign redirects to origins rather than application subpaths, do not add `/**` merely by convention.

After the final brand/domain decision:

```text
Site URL
https://cms.<brand>.nl/

Redirect URL
https://cms.<brand>.nl
```

Keep the old internal hostname temporarily only while a deliberate login/invite cutover requires compatibility; remove it when that transition is verified.

`http://localhost:3000` is a local-development value and must not remain the hosted project's production Site URL.

Supabase requires `redirectTo` destinations to match the configured Redirect URL allow list. The Site URL is only the fallback when application code provides no explicit redirect or a destination is not allowed.

Reference: https://supabase.com/docs/guides/auth/redirect-urls

## Invite email template rule

Use Supabase's standard `{{ .ConfirmationURL }}` for the invite template unless there is an observed need for a custom confirmation endpoint. `ConfirmationURL` carries the `redirect_to` generated by Auth.

A custom invite template must not construct the application destination from `{{ .SiteURL }}`. Use `{{ .ConfirmationURL }}` as the invite link; if a future template intentionally constructs its own destination, it must use `{{ .RedirectTo }}`.

Do not create a custom token-exchange/auth service merely to solve ordinary hosted redirects.

## Auth mail delivery contract

Supabase's built-in default SMTP service is suitable for development and bounded acceptance testing, but it is intentionally rate-limited and best-effort. At the time of this rollout the hosted default is limited to a very small number of Auth messages per hour; repeated invite testing can therefore return:

```text
HTTP 429
error_code = over_email_send_rate_limit
```

`team-invite` must surface this as a **mail-service quota** error, not as an e-mail-address or redirect error. A failed 429 invite must not leave a usable `team_members` record or hidden half-onboarded operator account.

For operational production onboarding and password recovery, configure a proven **custom SMTP provider** through Supabase rather than increasing application complexity or building a mailer. Provider choice is an infrastructure decision; SolidDesign remains coupled only to Supabase Auth's mail contract.

Production readiness therefore requires:

```text
Supabase Auth
→ custom SMTP configured
→ sender/domain verified
→ invite delivery tested
→ password recovery delivery tested
```

Do not hard-code SMTP credentials in the repository or browser.

Reference: https://supabase.com/docs/guides/auth/auth-smtp

## Verification gate

Before M1 invite/onboarding is marked browser-verified:

1. verify the visible environment marker before inviting;
2. verify the Team invite card shows the expected `Activatieomgeving` before sending;
3. invite from `pr-<number>` and confirm the server reports that exact preview as `activation_origin` and the email returns there;
4. confirm a mismatched or unapproved `invite_origin` is rejected;
5. finish first-password setup and verify `joined_at` is recorded only afterward;
6. verify a clean retry after an Auth mail-rate-limit failure creates no duplicate/half account;
7. repeat the redirect test after a future `cms.<brand>.nl` cutover before removing the old internal origin.

Before operational production onboarding:

1. configure custom SMTP in Supabase Auth;
2. verify an invite is delivered through that provider;
3. verify password recovery is delivered through that provider;
4. verify redirect behavior remains unchanged after SMTP cutover.

## Invariants

> Authentication redirects follow the explicitly requested and server-validated internal SolidDesign origin from which the invitation is created. Production and PR previews are visibly distinguishable; redirects never depend on a stale localhost Site URL and never follow arbitrary caller-supplied destinations.

> Mail transport is an infrastructure dependency of Supabase Auth, not a SolidDesign workflow subsystem. Use the platform's custom SMTP capability for production reliability rather than inventing a second invitation/mailer architecture.
