# Workflow 03 — Build and Iterate

## Goal

Build the smallest complete website concept that proves the chosen design direction.

## Mandatory production order

When the deliverable includes HTML, use this order:

1. confirm the diagnosis and inheritance map;
2. establish information architecture;
3. determine page composition;
4. define each required image role;
5. select or generate the strongest truthful image assets;
6. lock image identity, crop, aspect ratio, focal point and object-position;
7. build semantic HTML/CSS around those decisions;
8. make responsive behavior intentional;
9. render the actual HTML;
10. compare source/current concept → rendered candidate;
11. refine until further changes produce no material improvement.

Do not build prominent image boxes first and later fill them with whatever source thumbnails are available.

## Build rules

1. Build from the agreed diagnosis and design direction; do not restart from generic template defaults.
2. Use verified prospect facts. If content is missing, write neutral structural copy or omit the block rather than inventing proof.
3. Preserve identity and useful customer-recognizable terminology; do not mechanically preserve weak execution.
4. Keep hierarchy obvious: proposition → relevant proof/context → services/content → action.
5. Treat mobile as a real layout, not a compressed desktop version.
6. Avoid unnecessary components, animation, libraries and architectural changes.
7. Prefer a complete static HTML/CSS/JS bundle that can be uploaded to the SolidDesign CMS when the task allows it.
8. When one self-contained HTML file is practical, embed critical logo/imagery so the intended design survives CMS upload without source-site hotlinks or relative-path failures.
9. Use the exact locked image assets and crops. Do not substitute visually weaker “equivalent” images during implementation.
10. Do not enlarge low-resolution source imagery into dominant visual roles. Replace or re-art-direct it when the image-role plan requires higher quality.
11. Keep generated imagery grounded: use it for presentation, not as fabricated documentary evidence.
12. The prospect website speaks only as the prospect business to its customers. Never include design commentary, audit terminology, “current website”, “this concept”, “we moved”, SolidDesign/CMS language or redesign rationale in customer-facing copy.
13. Do not create a new reusable template or framework to solve one customer's design issue.

## HTML fidelity rule

The HTML is the design when HTML is the deliverable.

Do not create a polished standalone mock-up and then rebuild a weaker generic approximation. Render the final HTML and judge that actual result.

## Iteration discipline

For each meaningful revision:

- identify the specific problem being solved;
- change the smallest coherent set of elements that addresses it;
- preserve improvements already accepted;
- inspect actual image quality and crop, not just semantic relevance;
- record a concise version note describing the meaningful change;
- re-check desktop and mobile consequences;
- reject a revision that is merely different rather than materially better.

## Version note format

Keep it short and factual, for example:

```text
Hero proposition shortened; service hierarchy regrouped; mobile CTA simplified; weak source thumbnails replaced by locked art-directed imagery.
```

Do not use version notes as a design diary.
